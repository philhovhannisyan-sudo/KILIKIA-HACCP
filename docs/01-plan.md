## 1. Стек и обоснование (в рамках §3)

| Слой | Выбор | Почему |
|---|---|---|
| Среда | **Node.js ≥ 22 LTS**, **TypeScript** везде | Рекомендация §3.1; один язык для сервера, клиента и общих правил (валидация, разбор чисел, автоматы) — правила не расходятся между слоями. |
| HTTP-сервер | **Fastify** | Схемы маршрутов, хук `preHandler` для единой проверки прав, быстрый и простой. На каждом маршруте декларируется требуемое право; маршрут без декларации не регистрируется (проверка при старте + тест). |
| БД | **SQLite, один файл** `data/haccp.sqlite` через **better-sqlite3** | §3.1. Синхронные транзакции — «в одной транзакции» из фазы 4 (запись мониторинга + несоответствие + карантин + уведомление + журнал) реализуется буквально. Триггеры `BEFORE UPDATE/DELETE … RAISE(ABORT)` делают журнал, мониторинг и среду неизменяемыми **на уровне БД**, а не только API. Запасной вариант без нативной сборки — встроенный `node:sqlite` (тот же SQL, адаптер на 1 файл). |
| Миграции | Свои SQL-файлы `server/db/migrations/NNN_*.sql` + таблица версий | Прозрачно, без ORM; схема читается как документ (`docs/02-data-model.md`). |
| Валидация | **zod**, общие схемы в `shared/` | Один код проверки на клиенте (подсказки) и сервере (решение). |
| Аутентификация | Логин/пароль, хэш **scrypt** (`node:crypto`), серверная сессия в БД, cookie `httpOnly; SameSite=Strict` | Без нативных зависимостей; §3.5. |
| Клиент | **React 18 + Vite**, react-router | Зрелая экосистема для форм, таблиц, DnD; Vite собирает всё в локальный `dist/`, сервер отдаёт статику — никаких CDN (§3.3). |
| i18n | Свой тонкий слой: словари `ru/en/hy.json`, типизированные ключи, `Intl` для дат/чисел | Полный контроль над правилом «отсутствующий ключ = падение теста» и над переключением без перезагрузки (контекст React, состояние форм не теряется). Библиотека i18next избыточна. |
| DnD схемы процесса | **@dnd-kit** | Доступный (клавиатура), работает на тач-экранах. |
| Графики | **uPlot** | Маленький, быстрый для 14 дней × 4 точек среды и трендов ККТ; локальный пакет. |
| PDF | **pdfmake** (на сервере), шрифты **Noto Sans + Noto Sans Armenian** (OFL), TTF лежат в `assets/fonts/` | Чистый JS, без браузера в рантайме; `headerRows` даёт повтор шапки таблицы, колонтитулы с номером страницы и датой; перенос по словам. pdfmake не делает подстановку шрифта по символу, поэтому текст режется на «прогоны» по Unicode-диапазону (армянский → Noto Sans Armenian, остальное → Noto Sans) — общий помощник `scriptRuns()`. |
| XLSX / CSV | **exceljs** / свой CSV (UTF-8 BOM, `;`-разделитель для ru-Excel — см. вопрос-21) | Локально, без внешних сервисов. |
| Иконки | **lucide** (SVG, локально в бандле) | §3.3. |
| Тесты | **Vitest** (unit/интеграция API на временной БД) + **Playwright** (e2e, Chromium) | `npm test` запускает оба. Идентификатор теста = код критерия (`K05 …`). Скрипт `scripts/acceptance-report.mjs` пишет `docs/03-acceptance.md` из JSON-репортёров. |
| Время | Модуль `server/core/clock.ts` (подменяемые «часы» только в тестовом режиме) | Asia/Yerevan, окно 24 ч, просрочки, таймер отзыва (К19) тестируются детерминированно. |

**Одна команда запуска:** `npm start`. Скрипт `scripts/start.mjs` использует только встроенные модули Node и на чистой копии сам выполняет: `npm ci` (если нет `node_modules`) → сборку клиента (если нет `dist/`) → миграции → автосидинг (если БД пустая) → запуск сервера на `http://localhost:3000`. Интернет нужен только для `npm ci` и `npx playwright install chromium` (последнее — только для `npm test`). Во время работы — ни одного внешнего запроса (проверяется в К26: e2e блокирует все запросы не на `localhost`).

**Время в данных:** все моменты хранятся как ISO-8601 UTC; «деловые» даты (сроки, поверки, смены) считаются в `Asia/Yerevan` одной функцией `shared/time.ts`. Отображение — `Intl.DateTimeFormat(locale, { timeZone: 'Asia/Yerevan' })`. У записей событий два поля: `event_at` (ввод пользователя, не раньше `now − 24 ч`, не позже `now + 5 мин`) и `recorded_at` (сервер).

**Идентификаторы:** ULID (текст), генерируются в приложении. Это позволяет в одной транзакции создать несоответствие и запись мониторинга со взаимными ссылками без последующего `UPDATE` неизменяемой записи.

### 3.6 Правила целостности (сервер, §6)
1. Выпуск партии ГП без `batch_consumption` → отказ (guard автомата).
2. Отгрузка партии «Карантин»/«Заблокирована» → 422 с кодом и статусом партии (К20).
3. Удаление объекта с входящими ссылками → 409 со списком «тип — коды — количество» (`integrity.ts` по реестру ссылок, без `ON DELETE CASCADE`).
4. FEFO: есть более старая партия того же продукта с остатком и статусом «Выпущена» → предупреждение с кодом старшей партии; без `fefo_override_reason` → отказ.
5. Дубль сырья в рецептуре → отказ «объедините строки».
6. `audit_log`, `monitoring_record`, `env_record` (+ корректировки) — без UPDATE/DELETE, триггеры БД + отсутствие таких маршрутов.
7. Оборудование с истёкшей поверкой нельзя указать в записи мониторинга/среды → 422 с датой окончания поверки (К12).
8. Время события вне окна → 422 с допустимым окном.

## 4. Фазы 1–9 и тесты приёмки

Принципы для всех фаз:
- В каждой фазе прогоняются **все** тесты предыдущих фаз (`npm test`); результат — в `docs/03-acceptance.md` (код, статус, фактический вывод, скриншот).

## 5. Сквозные решения

- **RBAC в UI:** все изменяющие элементы — только через `ActionButton`/`Can` с атрибутом `data-action="<право>"`; элемент не рендерится без права. Это даёт проверяемый признак для К7. Сервер не доверяет UI.
- **Одна правда для цифр:** панель, экраны модулей, отчёты и пакет для аудита вызывают одни функции `server/queries/*`. Тест К24 и К5 сравнивают их выход.
- **Каркасы:** конфигурация `client/scaffolds/<код>.ts` (поля, колонки, KPI-запросы, описание будущего наполнения, ключи i18n) + один шаблон. 19 страниц вручную не пишутся.
- **Нормативка:** всё из `regulatory-refs.md` переносится в `shared/regulatory/*` с полем `verifyStatus: 'СВЕРИТЬ'`; UI показывает бейдж «DEMO / сверить с официальным текстом» везде, где используется. Ничего не добавляю из памяти.
- **Демо-данные:** даты в сиде **относительно дня сидинга** (Ереван), чтобы «просроченная CAPA», «истёкшая поверка P-01» и «14 дней среды» оставались верными в любой день запуска.
- **Печать:** один макет pdfmake (шрифты, колонтитул «стр. N из M · дата формирования · кто», повтор шапки, перенос по словам); кнопка «Печать» в UI открывает тот же PDF. Плюс `@media print` скрывает навигацию при печати страницы браузером.

## 7. Открытые вопросы

Предложение по умолчанию указано в каждом вопросе; если согласны — достаточно ответить «по умолчанию». Нормативные вопросы (2–6) также внесены в `docs/regulatory-refs.md` §6.

**Процесс и источники**
- **вопрос-1.** Файл `HACCP_Suite_ClaudeCode_prompt_131026.md` (v1) считаю устаревшим и следую только брифингу v2 (7 экранов мастера, без ответа «Не применимо», цель отзыва — настройка). *По умолчанию: да, v1 не используется и в репозиторий не кладётся.*

**Нормативка (`regulatory-refs.md`)**
- **вопрос-2.** Дерево решений, В1а «Да» → «изменить стадию, процесс или продукт → вернуться к В1». Брифинг допускает только результаты «ККТ» / «не ККТ». Как фиксировать этот исход? *По умолчанию: третий результат «Требуется изменение» — блокирует отправку плана на утверждение, пока опасность не пересмотрена.*
- **вопрос-3.** Категоризация OPRP (refs §2): как критерии 1–4 влияют на результат, и что делать, если по правилу DEMO мера «кандидат в ККТ», а дерево дало «не ККТ»? Когда результат «PRP» для значимой опасности? *По умолчанию: критерии 1–5 — «Да/Нет» + обоснование, все обязательны; критерий 5 «Да» → предупреждение «кандидат в ККТ, пересмотрите ответы дерева» (результат не ставится); критерий 5 «Нет» и критерий 3 «Да» → OPRP; иначе → PRP. Правило помечено DEMO.*
- **вопрос-4.** Целевое время: одно значение для теста прослеживаемости и для тестового отзыва или два? *По умолчанию: две настройки, обе 4 ч DEMO, пометка «СВЕРИТЬ BRCGS 3.9 / 3.11».*
- **вопрос-5.** Номера разделов ISO/TS 22002-1 для реестра PRP в refs §4 не даны (только названия). Пришлёте номера? *По умолчанию: показываю только собственные названия, поле номера пустое с `TODO(вопрос-5)`.*
- **вопрос-6.** Правила зачёта готовности (refs §5): (а) «записи верификации за период» — какой период и что считается записью верификации? (б) пункты 7.5, 9.2, 9.3 зависят от каркасов D07, D05, D08 — засеять ли там данные так, чтобы пункты были покрыты? *По умолчанию: (а) последние 30 дней; запись верификации = завершённая проверка результативности CAPA, чек-лист PRP или проверка металлодетектора на эталонах; (б) засеять: 7.5 и 9.3 покрыты, 9.2 — нет. Итог демо-готовности задаётся сидом осознанно, а не случайно (ориентир: 8.7 и 10.1 не покрыты из-за P-01 и просроченной CAPA).*

**Данные и журнал**
- **вопрос-7.** Сброс демо-данных удаляет всё, включая журнал, что противоречит «журнал не удаляется». Кто может сбрасывать (кнопка в верхней панели у всех?) и что происходит с журналом? *По умолчанию: сброс — только `admin`, с модальным подтверждением; БД пересоздаётся, новый журнал начинается записью «сброс» с хэшем последней записи прежнего журнала; перед сбросом автоматически сохраняется бэкап в `data/backups/`.*
- **вопрос-8.** Нормализация дампа для К9. *По умолчанию: в дамп входят все бизнес-таблицы, файлы (sha256) и журнал аудита; не входят `session`, `login_event` и системные записи журнала «экспорт/сброс/импорт»; строки сортируются по id, JSON канонический.*
- **вопрос-9.** OPRP-1 имеет два параметра (Brix и pH, два прибора), ККТ-2 — три эталона с результатом «сработал/не сработал», а в §6 у ККТ один `мин/макс/единица`. *По умолчанию: ККТ/OPRP → 1..n параметров, тип параметра «число» или «да/нет»; для «да/нет» вне предела = «не сработал».*
- **вопрос-10.** Где и когда можно менять критический предел? *По умолчанию: `ccp.limit.update` есть у `haccp.lead` и `admin`; правка разрешена только для плана в состоянии «Черновик»/«На пересмотре» (через A01 экран 6 или реестр A03 — это одна сущность); для утверждённого плана — 409 с перечнем переходов (К15). Проверка права идёт раньше проверки состояния, поэтому `operator` всегда получает 403 с названием права (К6).*
- **вопрос-11.** Корректировки записей мониторинга/среды: кто может их вносить, и что если исправленное значение выходит за предел (или возвращается в предел)? *По умолчанию: вносят `qa.lab`, `haccp.lead`, `admin`, а `operator` — только свои записи в пределах окна 24 ч; корректировка «за предел» запускает ту же транзакцию, что и исходная запись (НС + карантин); возврат «в предел» НС не закрывает — только через автомат D04.*
- **вопрос-12.** Отклонение в A10 (среда) создаёт несоответствие автоматически, как ККТ, или только уведомление? *По умолчанию: уведомление + отметка «вне предела»; несоответствие — кнопкой «Зарегистрировать НС» (источник = запись среды). Без привязки к партии и без карантина.*
- **вопрос-13.** Справочные наименования (продукты, сырьё, стадии, склады, площадка) показывать на языке интерфейса? *По умолчанию: да — справочники хранят `name_i18n` (ru/en/hy) и засеяны на трёх языках; свободный текст пользователя (описания, обоснования) хранится как введён.*
- **вопрос-14.** Формы каркасов: работают или только показывают поля? *По умолчанию: у B03, C01, C03, D03 формы работают на полных данных (партии, расход, отгрузка с проверками, поверки); у остальных 15 каркасов форма показывает поля, а кнопка «Сохранить» неактивна с подсказкой «в разработке».*
- **вопрос-15.** Автомат «Выпуск партии» для сырья тоже? Что возвращает партию из карантина после несоответствия? *По умолчанию: один автомат для партий ГП и сырья (guard «есть расход сырья» только для ГП); новые партии создаются в «Карантине»; выход из карантина — переход «Проверки выполнены» вручную с guard «нет открытых НС по партии»; права — `qa.lab`, `haccp.lead`.*
- **вопрос-16.** Пересмотр плана: ККТ при новой версии — те же сущности? Какая версия попадает в пакет, если за период действовало несколько? *По умолчанию: `control_point` живёт на уровне линии версий плана (тот же id, пока код ККТ не меняется; записи мониторинга хранят снимок пределов); в пакет — все версии, действовавшие в периоде.*
- **вопрос-17.** Ввод времени события в будущем. *По умолчанию: запрещён, допуск +5 мин на расхождение часов.*
- **вопрос-18.** «Технический директор» — в §7 ограничений нет. Это только чтение + KPI/отчёты/анализ руководства, или полные права на изменение? *По умолчанию: чтение всего + права на D08 (анализ руководства) и E01 (отчёты); без изменения записей других модулей.*
