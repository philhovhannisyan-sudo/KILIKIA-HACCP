## 1. Цель и контекст

Веб-приложение HACCP Suite — система управления пищевой безопасностью для производителя варенья, джемов и конфитюров. 26 модулей в 5 группах (A–E) на одной модели данных, одном движке процессов и одном журнале аудита.

Нормативная база (официальные написания, не переводить вольно):
- ТР ТС 021/2011 «О безопасности пищевой продукции», ст. 10 — правовое основание процедур на принципах ХАССП в ЕАЭС;
- Codex Alimentarius CXC 1-1969 (ред. 2020);
- ISO 22000:2018;
- ISO/TS 22002-1;
- BRCGS Food Safety (Issue 9).

Любая формулировка вопроса, номер пункта или числовой норматив берётся **только** из `docs/regulatory-refs.md`. Если нужного там нет — не придумывать, а задать вопрос и оставить в коде TODO со ссылкой на вопрос.

## 2. Границы MVP

**Ключевое правило:** модель данных и бизнес-правила полны для всех сущностей, которые используют MVP-модули (партии, отгрузки, оборудование и поверки, склад и FEFO, связь «ГП → сырьё»). «Каркасом» является только пользовательский интерфейс модуля, а не его данные.

Функционально полные модули (7): A01, A02, A03, A04, A10, D04, E01.
Каркасы (19): A05–A09, B01–B03, C01–C03, D01–D03, D05–D08, E02.

Каркас — не пустая страница: маршрут, панель с показателями из реальных данных, таблица с демо-данными, форма с полями, печатная форма-заготовка и видимая пометка «в разработке» с описанием будущего наполнения. Каркасы генерируются из конфигурации модуля (поля, колонки, описание) по одному общему шаблону, а не пишутся вручную 19 раз.

## 3. Архитектурные рамки

Стек выбирает исполнитель и обосновывает в `docs/01-plan.md`, но в следующих рамках:

1. **Локальный бэкенд обязателен.** Права и правила целостности проверяются на сервере. Чисто клиентское хранилище (localStorage/IndexedDB как основная БД) не допускается: оно делает RBAC и неизменяемость журнала обходимыми через DevTools. Рекомендуемый вариант: Node.js + SQLite (один файл БД); допустимы альтернативы с тем же свойством.
2. **Запуск одной командой** из README на чистой копии репозитория. Среда исполнения работает полностью без интернета; установка зависимостей и браузеров Playwright при первом запуске интернет использовать может.
3. **Все ресурсы локальны:** шрифты (включая армянские), библиотеки PDF и Excel, иконки. Никаких CDN во время работы.
4. **Часовой пояс:** Asia/Yerevan. Время записи — серверное. Ввод фактического времени события разрешён не ранее чем на 24 ч назад (DEMO-значение настройки); оба времени хранятся.
5. **Аутентификация:** вход по логину и паролю для демо-пользователей (раздел 7). В демо-режиме на экране входа виден список учёток. Реальная 2FA/SSO — вне scope.

## 5. Фазы реализации

Каждая фаза заканчивается остановкой и ожиданием подтверждения пользователя. Одна фаза — одна сессия; контекст восстанавливается из `docs/`.

### Фаза 0 — План (без кода)
Прочитать этот файл, `CLAUDE.md`, `docs/regulatory-refs.md`. Написать `docs/01-plan.md`: стек и обоснование в рамках раздела 3, структура папок, схема БД, список фаз, перечень тестов приёмки с привязкой к фазам, список открытых вопросов.
**Ворота:** подтверждение плана.

### Фаза 1 — Оболочка, i18n, тестовый контур
- Структура проекта, одна команда запуска, README, `npm test` (или аналог) с unit и e2e.
- Оболочка: боковое меню (5 групп, 26 пунктов), верхняя панель (язык, пользователь и роли, выход, сброс демо-данных), область контента, модальные окна, уведомления, хлебные крошки.
- Маршрут на каждый модуль (пока заглушки фазы 1 с пометкой).
- i18n ru/en/hy (раздел 8).
- Адаптив: при ширине < 820px меню становится горизонтальной полосой вкладок.
- Тесты фазы: К1, К2, К3, К4 (в режиме оболочки).

### Фаза 2 — Данные, аутентификация, RBAC, журнал аудита
- Схема БД (раздел 6), слой доступа с единой точкой проверки прав.
- Демо-данные (раздел 12), автосидинг при первом запуске, сброс.
- Экспорт/импорт состояния файлом (только администратор; импорт фиксируется в журнале).
- Вход, демо-пользователи, RBAC (раздел 7).
- Журнал аудита: append-only, хэш-цепочка, снимок имени и ролей на момент записи; исправление записей только через запись-корректировку.
- Конечные автоматы как данные (раздел 9).
- Тесты: К5–К10.

### Фаза 3 — A01 Конструктор плана ХАССП
Мастер из 7 экранов, прогресс «n/7». Соответствие 12 шагам Codex:

| Экран | Шаги Codex / принципы |
|---|---|
| 1. Группа ХАССП | шаг 1 |
| 2. Продукт и предполагаемое использование | шаги 2–3 |
| 3. Схема процесса + подтверждение на месте (дата, кто) | шаги 4–5 |
| 4. Анализ опасностей (стадия × тип био/хим/физ/аллерген × вероятность × тяжесть × мера контроля) | шаг 6 / принцип 1 |
| 5. Определение ККТ (дерево решений) и категоризация OPRP | шаг 7 / принцип 2 |
| 6. Пределы, мониторинг, корректирующие действия | шаги 8–10 / принципы 3–5 |
| 7. Верификация, документирование, утверждение | шаги 11–12 / принципы 6–7 |

- Схема процесса для демо: приёмка сырья → мойка/инспекция → подготовка фруктов → варка → стерилизация тары → фасовка (горячий розлив) → укупорка → охлаждение → обнаружение металла → маркировка → хранение. Порядок меняется drag-and-drop.
- **Дерево решений** — конфигурация в данных; формулировки вопросов, ветвления и подвопрос «необходим ли контроль на этой стадии» берутся из `docs/regulatory-refs.md`. Каждый ответ: «Да / Нет» + обязательное обоснование. Результат: «ККТ» или «не ККТ».
- **Категоризация OPRP** — отдельный шаг для значимых опасностей, контролируемых не в ККТ, по критериям из `docs/regulatory-refs.md` (ISO 22000:2018, 8.5.2.4). Результат: «OPRP» или «PRP».
- Экран 6 создаёт и обновляет записи реестра ККТ/OPRP, которые использует A03 (единая сущность, не копия).
- Утверждение плана — только роль «Руководитель ХАССП». Утверждённый план меняется только через переход «На пересмотре» с новой версией.
- PDF плана ХАССП по форме (раздел 11).
- Тесты: К13–К16.

### Фаза 4 — A03 Мониторинг + A10 Среда и холодовая цепь
- Реестр ККТ/OPRP (из A01): номер, тип, стадия, опасность, пределы мин/макс, единица, метод, частота, ответственный, оборудование, корректирующее действие.
- Форма мониторинга: ККТ, партия, значение, время события, оператор (текущий пользователь), оборудование. Оборудование с истёкшей поверкой недоступно для выбора, причина и дата окончания поверки показаны.
- Значение вне предела → в одной транзакции: запись мониторинга, несоответствие (связано с записью и партией), перевод партии в «Карантин», уведомление, записи журнала аудита.
- A10: точки измерения по зонам, журнал T°/влажности, графики, отклонения.
- Графики тренда по каждой ККТ.
- Тесты: К11, К12, К17.

### Фаза 5 — A04 Прослеживаемость и отзыв
- Дерево назад: партия ГП → партии сырья/упаковки → поставщики. Вперёд: партия ГП → отгрузки → клиенты.
- **Тест прослеживаемости** с таймером и контролем целевого времени (норматив — из `docs/regulatory-refs.md`; при отсутствии подтверждённого значения — настройка с DEMO-значением 4 ч и пометкой).
- **Тестовый отзыв:** выбор партии, список затронутых отгрузок, отметка «возвращено», % возврата, время реакции, отчёт.
- Превышение целевого времени → отчёт помечен как несоответствие и создаёт запись в D04.
- Тесты: К18–К20.

### Фаза 6 — A02 PRP/OPRP + D04 Несоответствия и CAPA
- A02: реестр PRP по разделам ISO/TS 22002-1 (здания, вода, воздух, отходы, мойка, вредители, персонал, обучение и т. д. — перечень разделов из `docs/regulatory-refs.md`), OPRP (из A01), чек-листы периодической оценки, доказательства (файлы, хранятся локально).
- D04: источник (мониторинг ККТ, входной контроль, аудит, претензия, отзыв) → «5 почему» + Исикава 6M → CAPA (ответственный, срок) → проверка результативности → закрытие. Жизненный цикл — конечный автомат.
- Тесты: К21–К22.

### Фаза 7 — E01 Отчётность и пакет для аудита
- Конструктор отчётов: модуль, период, поля, группировки, предпросмотр; экспорт CSV, XLSX, PDF.
- Пакет для аудита за период — один PDF: титул, оглавление, план ХАССП (действующая версия на период), записи ККТ/OPRP, прослеживаемость (тесты за период), доказательства CAPA, дата формирования, кто сформировал (имя и роли).
- Отчётные цифры считаются тем же кодом запросов, что и экраны модулей.
- Тесты: К23–К24.

### Фаза 8 — Каркасы 19 модулей + E02
- Общий шаблон каркаса + конфигурация каждого модуля.
- E02: пользователи, роли, права, журнал входов, просмотр и проверка целостности журнала аудита, бэкап/восстановление, мультиплощадка (заготовка).
- Тесты: К25.

### Фаза 9 — Финальная приёмка
- Полный прогон тестов, `docs/03-acceptance.md` с фактическими результатами.
- Скриншоты в `docs/evidence/`: главная, план ХАССП, мониторинг, прослеживаемость, CAPA, пакет для аудита, 390px, три языка, PDF на hy.
- Проверка README на чистой копии.
- Тесты: все, включая К26.

## 6. Модель данных

Сущности (минимальный набор):

**Платформа**
- Пользователь — имя, логин, хэш пароля, роли[], активен.
- Роль — код, права[].
- Право — `модуль.объект.действие` (например `ccp.limit.update`).
- Запись журнала аудита — серверное время, пользователь, **имя и роли на момент записи**, модуль, объект, id объекта, действие, до/после, комментарий, хэш предыдущей записи, собственный хэш.
- Запись входа — пользователь, время, результат.
- Площадка — код, наименование (одна активная в MVP).

**Производство и склад**
- Продукт — код, наименование, спецификация, срок годности, упаковка, пищевая ценность.
- Рецептура (BOM) — продукт, версия, действует с, строки: сырьё + норма на единицу.
- Партия сырья/упаковки — код, материал, поставщик, дата приёмки, срок годности, количество, статус, документы.
- Партия ГП — код, продукт, дата изготовления, линия, смена, количество, статус.
- Расход «партия ГП → партия сырья» — фактическое количество.
- Склад, остаток — склад, партия, количество, срок годности, статус.
- Поставщик — наименование, рейтинг, статус одобрения, документы и их сроки.
- Клиент; Отгрузка — номер, клиент, дата, позиции (партия + количество), T° при перевозке.

**ХАССП и безопасность**
- План ХАССП — версия, статус, данные экранов мастера, дата, ответственный, дата подтверждения схемы на месте.
- Стадия процесса — план, порядок, наименование.
- Опасность — стадия, тип, описание, вероятность, тяжесть, значимость, мера контроля, ответы дерева решений с обоснованиями, результат (ККТ/OPRP/PRP/не значима).
- ККТ/OPRP — код, тип, стадия, опасность, мин/макс, единица, метод, частота, ответственный, оборудование, корректирующее действие.
- Запись мониторинга — ККТ, партия, значение, время события, серверное время, оператор, оборудование, в пределах/вне, ссылка на несоответствие.
- Запись-корректировка — ссылка на исходную запись, новое значение, причина, автор, время. Исходная запись не изменяется.
- Точка измерения среды — зона, тип, мин/макс, оборудование; Запись среды — точка, значение, время, в пределах/вне.
- PRP — код, раздел ISO/TS 22002-1, описание, частота, последняя проверка, статус; Пункт чек-листа PRP — вопрос, результат, примечание, доказательство.
- Тест прослеживаемости / Тестовый отзыв — тип, дата, партия, старт/финиш, длительность, затронутые отгрузки, возвращено/всего, %, соответствие целевому времени.

**Качество**
- Оборудование — код, наименование, зона, последняя/следующая поверка, статус, свидетельство.
- Несоответствие — источник (тип + id), партия, описание, тяжесть, статус, первопричина, CAPA[].
- «5 почему» — шаги[], первопричина; Исикава — категория 6M, причины[].
- CAPA — мероприятие, тип, ответственный, срок, статус, проверка результативности (дата, результат, проверил).
- Каркасы: лабораторная проба, аудит, претензия, документ.
- Пункт стандарта — стандарт, номер, краткое собственное название, правило зачёта (раздел 10).

**Целостность (проверяется на сервере)**
- Партия ГП без связей с сырьём не может быть выпущена.
- Партия в «Карантине» или «Заблокирована» не может быть отгружена; сообщение называет партию и статус.
- Удаление объекта, на который есть ссылки, отклоняется с перечнем блокирующих ссылок (типы, коды, количества).
- FEFO: отгрузка партии при наличии более старой партии того же продукта — предупреждение с кодом старшей партии и требованием обоснования.
- Одно сырьё дважды в одной рецептуре — отказ с просьбой объединить строки.
- Записи мониторинга, среды, журнала аудита не изменяются и не удаляются; исправление — только записью-корректировкой.

## 7. RBAC и демо-пользователи

| Роль | Основные права | Ограничения |
|---|---|---|
| Администратор | всё, пользователи и роли, настройки, бэкап/импорт | — |
| Руководитель ХАССП | утверждение плана ХАССП, CAPA, документы, анализ руководства | без управления пользователями |
| Технолог / производство | партии, протокол партии, рецептуры, планирование | без утверждения CAPA |
| Оператор линии | записи мониторинга ККТ и среды, отбор проб | **не изменяет критические пределы** |
| Качество / лаборатория | контроль качества, LIMS, несоответствия, оборудование | без управления пользователями |
| Склад | приёмка, размещение, отгрузка | без доступа к плану ХАССП |
| Технический директор | KPI, анализ руководства, отчёты | — |
| Внешний аудитор | **только чтение** + формирование пакета для аудита | ни одной кнопки изменения |

Правила:
- Права объединяются по всем ролям пользователя.
- Скрытая кнопка не является запретом: сервер отклоняет действие, отправленное напрямую в API, с сообщением, какого права не хватает.
- Смена ролей пользователя не меняет прошлые записи журнала.

Демо-учётки (пароль `demo` у всех, DEMO): `admin`, `haccp.lead`, `technologist`, `operator`, `qa.lab`, `warehouse`, `tech.director`, `auditor`, `qa.tech` (две роли: Качество + Технолог).

## 8. i18n (ru / en / hy)

- Один словарь, одинаковые ключи. Отсутствующий ключ в любом языке — падение теста, а не пустая строка.
- Переключение без перезагрузки и без потери введённых в форме данных.
- Даты, время, числа по локали (`ru-RU`, `en-GB`, `hy-AM`).
- **Ввод чисел** принимает и запятую, и точку как десятичный разделитель во всех локалях; хранится нормализованное число.
- **Терминология:** `docs/glossary.csv` (ключ, ru, en, hy) для 40–60 ключевых терминов. Армянские значения создаёт исполнитель, в файле и в README отмечено «hy — требует вычитки носителем». UI использует термины только через глоссарий.
- Длинный армянский текст переносится по словам; коды и числа не переносятся.
- Печатные формы на текущем языке, включая подписи граф.
- Названия стандартов не переводятся.

## 9. Движок процессов (конечные автоматы в данных)

1. **Несоответствие:** Зарегистрировано → В анализе → Первопричина определена → CAPA назначено → CAPA выполнено → Проверка результативности → Закрыто; из проверки возможен возврат «Признано нерезультативным» → В анализе.
2. **План ХАССП:** Черновик → На утверждении → Утверждён → На пересмотре → (новая версия) Черновик…; старая версия → Архив.
3. **Выпуск партии:** Карантин → Проверки выполнены → Выпущена | Заблокирована → Утилизация | Переработка.
4. **CAPA:** Запланировано → В работе → Выполнено → Проверено → Закрыто.
5. **Документ (каркас):** Черновик → На утверждении → Действующий → На пересмотре → Отменён.

Требования:
- Таблица переходов в данных: откуда, куда, требуемое право, нужен ли комментарий, проверки-условия.
- Каждый переход пишется в журнал (кто, когда, роли, было → стало, комментарий).
- Недопустимый переход отклоняется с перечнем доступных переходов.

## 10. Панель готовности к аудиту (главная)

Показатели:
1. **Готовность, %** = покрытые пункты / все пункты из `docs/regulatory-refs.md` (раздел «Пункты для расчёта готовности»). Пункт покрыт, если к нему привязан утверждённый документ или запись, актуальная на текущую дату по правилу пункта. Тексты стандарта не включаются — только номера и собственные краткие названия.
2. **Открытые CAPA** — количество и список, просроченные выделены.
3. **Просроченные поверки** — количество и перечень оборудования.
4. **Партии на карантине** — количество и перечень.

Дополнительно: последние отклонения ККТ, ближайшие сроки (пересмотр документов, поверки, проверки PRP).
Цифры считаются тем же кодом, что и в модулях. Расхождение — дефект.

## 13. Критерии приёмки

Каждый критерий — автоматический тест (Playwright для e2e, unit для логики), идентификатор теста = код критерия. Результат прогона пишется в `docs/03-acceptance.md`: код, статус, фактический вывод, ссылка на скриншот.

**Оболочка**
- К1. Все 26 маршрутов открываются без ошибок и пустых экранов.
- К2. Переключение ru → en → hy меняет интерфейс, меню и печатные формы без перезагрузки; введённые в открытой форме данные сохраняются.
- К3. На ширине 390px во всех 26 разделах `document.documentElement.scrollWidth <= document.documentElement.clientWidth`.
- К4. На 390px и 1280px во всех языках ни у одной кнопки, заголовка или ячейки нет `scrollWidth > clientWidth` при `overflow: hidden`.

**Данные, права, журнал**
- К5. Чистый запуск содержит объёмы из раздела 12; цифры совпадают с панелью готовности.
- К6. `operator` получает отказ сервера при прямом API-запросе на изменение предела ККТ; сообщение называет недостающее право.
- К7. `auditor` не видит ни одного элемента изменения во всех 26 разделах и может сформировать пакет для аудита.
- К8. Попытка изменить или удалить запись журнала отклоняется; запись хранит имя и роли на момент внесения; после смены ролей пользователя запись не меняется; проверка хэш-цепочки проходит.
- К9. Экспорт → сброс → импорт: хэш нормализованного дампа до и после совпадает.
- К10. Исправление записи мониторинга создаёт запись-корректировку с причиной; исходная запись видна и не изменена.

**ККТ и несоответствия**
- К11. Значение вне предела создаёт несоответствие, связанное с записью и партией, переводит партию в «Карантин»; несоответствие видно в D04 с источником.
- К12. P-01 нельзя выбрать в форме мониторинга; сообщение содержит дату окончания поверки. Прямой API-запрос с P-01 отклоняется.
- К17. Ввод «85,5» и «85.5» даёт одно и то же сохранённое значение во всех локалях.

**План ХАССП**
- К13. Мастер проходит 7 экранов с прогрессом; план утверждается ролью `haccp.lead`; другая роль получает отказ.
- К14. Дерево решений детерминировано: одинаковые ответы → одинаковый результат; ветки соответствуют `docs/regulatory-refs.md` (тест на каждую ветку).
- К15. Изменение утверждённого плана без перехода «На пересмотре» отклоняется с перечнем допустимых переходов.
- К16. ККТ, определённая в A01, появляется в реестре A03 как та же сущность.

**Прослеживаемость**
- К18. Для демо-партии дерево назад показывает все партии сырья и поставщиков, вперёд — все отгрузки и клиентов.
- К19. Тестовый отзыв выдаёт отчёт с длительностью, числом отгрузок и % возврата; превышение целевого времени помечает отчёт и создаёт несоответствие.
- К20. Отгрузка партии на карантине отклоняется с указанием партии и статуса.

**CAPA**
- К21. Несоответствие нельзя закрыть без заполненной проверки результативности CAPA.
- К22. Чек-лист PRP сохраняет доказательство-файл и выводит его в печатную форму.

**Пакет для аудита**
- К23. Пакет за период содержит титул, оглавление, 4 раздела, дату формирования, имя и роли сформировавшего.
- К24. Количества записей и ключевые значения в пакете совпадают с экранами модулей за тот же период.

**Каркасы**
- К25. Каждый из 19 каркасов имеет панель, таблицу с данными, форму, печатную заготовку и пометку «в разработке» с описанием.

**Запуск и качество**
- К26. На чистой копии команда из README поднимает приложение без ручных шагов и без интернета во время работы; сброс возвращает демо-состояние; консоль браузера без ошибок на всём e2e-прогоне; PDF на hy отображает армянский текст (проверка извлечением текста из PDF).
